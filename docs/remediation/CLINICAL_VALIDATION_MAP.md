# Clinical Validation Map — Phase 2

Status: Phase 2 closure implementation map for typed clinical schema, registry validation, trusted evidence binding, server-authoritative status metadata, and abstention. This map is based on inspected code paths and does not assert clinical approval, formal validation, compliance, production readiness, or official registry readiness.

## Trusted Source Boundary

- Trusted patient facts may come from current patient input and extracted document text after Phase 1 outbound/browser sanitization boundaries. Evidence text authored by a provider remains untrusted until it is deterministically matched back to those trusted inputs.
- Trusted registry facts may come only from an approved synthetic test fixture or a future approved registry release. Local `backend/data_terstruktur/*` files are not approved and do not activate authoritative grounding.
- Trusted status metadata is server-derived: `clinical_status`, `accepted_recommendations`, `validation_status`, `nurse_review_required`, registry version, and registry source are computed or overwritten by backend validation code.
- Provider output is always untrusted. Provider-authored `patient_fact`, `source`, `validation_status`, `nurse_review_required`, `confidence_band`, `registry_version`, `registry_source`, and any approval/provenance claims cannot bypass abstention.

## Closure Hardening Notes

- Evidence binding now checks each provider-authored evidence item against trusted patient context using allowed evidence sources, exact clinical measurement matching, negation-polarity preservation, and conservative token containment. Unsupported, contradictory, or provider-draft-only evidence triggers abstention.
- Strict parsing accepts only bounded raw JSON objects. Raw prose, Markdown-fenced JSON, leading/trailing prose, duplicate JSON keys, unknown fields, empty objects, oversized responses, and deeply nested responses fail closed.
- `/chat`, `/chat_stream`, `/analisis`, and `/analisis_multi` fail fast before provider construction when the approved registry set is unavailable or incomplete. Missing diagnosis registry returns `registry_unavailable`; missing outcome/intervention registries return `registry_incomplete`. Streamed responses expose machine-readable status through `X-Clinical-Status`, `X-Accepted-Recommendations`, `X-Nurse-Review-Required`, and `X-Validation-Issue-Codes` headers.
- Partial registry availability contract for Phase 2 closure: selected interim safe default is complete care-plan abstention. For 3S, approved SDKI without approved SLKI and SIKI returns `clinical_status=registry_incomplete`, `accepted_recommendations=false`, and lists missing registries. For 3N, approved NANDA without approved NOC and NIC behaves the same. Missing components are never fabricated from model memory.

## Implementation Boundary

Phase 2 adds typed schema validation, synthetic-fixture registry validation, trusted evidence containment, server-authoritative clinical status metadata, fail-fast approved-registry checks, and safe abstention at the backend clinical output boundary. It does not approve or enrich local registry data, enable external capabilities by default, harden Mermaid rendering, isolate parsers, add OCR, add authentication controls, add vector retrieval, or redesign audit storage.
